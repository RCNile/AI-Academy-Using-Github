How to Contribute

The whole loop, in six commands. Run them one at a time and read what each one prints back — Git is unusually chatty, and it's usually telling you something useful. 

# 1. Download the project
git clone https://github.com/RCNile/AI-Academy-Using-Github.git
cd AI-Academy-Using-Github

# 2. Make your own branch (put your name in it)
git checkout -b feature/add-your-name

# 3. Edit a file and save it, then check what changed
git status

# 4. Stage the file you want to save
git add team.html

# 5. Commit it, with a message describing what you did
git commit -m "Add Jane Smith to team page"

# 6. Upload your branch
git push origin feature/add-your-name

Git prints a link after step 6. Open it, write a sentence about what you changed, and click Create pull request. That's the whole workflow — the same one used on production software every day.

If You Get Stuck

Two commands solve most confusion:

git status usually suggests the exact command you need next. Run it before anything else.

📚 Clone a Repository

In plain English

Cloning downloads a complete copy of a project from GitHub onto your computer — every file, and the entire history of every change ever made to it.

The command

git clone https://github.com/RCNile/AI-Academy-Using-Github.git
cd AI-Academy-Using-Github

The second line moves you into the folder that was just created. Forgetting it is the single most common beginner stumble — Git commands only work inside the project folder.

When you'd do this

Once per project. After that you already have it — use git pull to fetch other people's newer changes rather than cloning again.

Common mistake fatal: destination path already exists means you've already cloned it. Don't clone again — cd into the folder you have and run git pull.

Download vs clone

GitHub's "Download ZIP" button gives you the files but not the history, and no connection back to GitHub. You can't commit or push from a ZIP. Clone instead — almost always.

🌿 Create Branches

In plain English

A branch is your own private copy of the project to experiment in. You can change anything, break anything, and the version everyone else is using stays exactly as it was.

Think of it as duplicating a slide deck before a big redesign, so the original is still there if the new direction doesn't work out.

The command

git checkout -b feature/add-jane-smith

-b means "create this branch, then switch to it". Without -b, Git expects the branch to exist already.

Naming branches

Most teams use a short prefix describing the kind of work:

  • feature/add-team-member — something new
  • fix/broken-footer-link — repairing something
  • docs/clarify-setup-steps — documentation only

Include your name or the specific task. my-branch tells nobody anything.

Useful commands

git branch          # list branches; * marks the one you're on
git checkout main   # switch back to the main branch
git switch main     # newer, clearer name for the same thing
Why bother, on a small change? Because unfinished work on main is instantly everyone's problem. On a branch, it's yours alone until you're ready to share it.

📝 Commit Changes

In plain English

A commit is a save point with a note attached. Unlike saving a document, committing never overwrites anything — every previous version stays available forever.

The commands

git status                              # what have I changed?
git diff                                # exactly which lines?
git add team.html                       # stage this file
git commit -m "Add Jane to team page"   # save the snapshot

Why two steps?

git add then git commit feels redundant at first. It exists so you can commit some changes and not others — if you edited four files but only two are finished, you stage those two.

git add is "put this in the box". git commit is "seal the box and label it".

Writing the message

Finish the sentence "If applied, this commit will…"

  • Add Jane Smith to team page — clear and specific
  • Fix broken GitHub link in footer — says what and where
  • update — update what?
  • fixed stuff — which stuff?
Common mistake Please tell me who you are means Git doesn't know your name yet. Run this once and it's solved for every project: 
git config --global user.name "Your Name"
git config --global user.email "you@nilehq.com"
Commit small and often Many small commits are far easier to review — and far easier to undo — than one enormous one. A commit per logical change is a good rhythm.

🚀 Push to GitHub

In plain English

Committing saves your work on your own computer. Pushing uploads those commits to GitHub, where teammates can see them.

Until you push, your work exists in exactly one place — and a laptop that gets lost or dies takes it with it.

The command

git push origin feature/add-jane-smith

origin is Git's default nickname for "the copy on GitHub I cloned from". Then the name of the branch you're sending.

Pull vs push

  • git push — send my commits up to GitHub
  • git pull — bring everyone else's commits down to me

Pull before you start work. Push when you've finished a piece.

Common mistake Updates were rejected because the remote contains work that you do not have means someone pushed while you were working. Fetch their changes first: 
git pull
git push
Never reach for git push --force to make this go away. It overwrites their work.
Authentication GitHub stopped accepting account passwords on the command line in 2021. If you're prompted for one, use gh auth login or paste a Personal Access Token instead. Full walkthrough in the README.

🔀 Open Pull Requests

In plain English

A pull request says: "Here's my change. Please look at it before we make it official." It's the conversation that happens around a change, before it joins the main project.

The name is confusing and everyone agrees. You're not requesting a pull — you're asking the project to pull your work in. Everyone calls them "PRs".

How to open one

  1. Push your branch. Git prints a link — that's the quickest route.
  2. Or go to the repo on GitHub; a banner offers to open a PR for any branch you've pushed recently.
  3. Write a title and a short description of what you changed and why.
  4. Click Create pull request.

What makes a good description

  • What changed — in one sentence
  • Why — the reason, which the code itself can't tell anyone
  • How to check it — what a reviewer should look at

Review isn't criticism

Someone will read your change and may ask questions or suggest edits. That's the point of the process — it catches problems cheaply, and it's how everyone stays aware of what's changing. Questions on your PR are not a judgement on your work.

This is where non-developers spend most time Reading PRs, leaving comments, approving designs. You can comment on any individual line of a change — you never need to touch the command line to take part.

✅ Merge Code

In plain English

Merging combines your branch back into the main project. Once your pull request is approved, clicking Merge pull request makes your change part of the real thing.

Who does it

On most teams, whoever reviewed it — or you, once you have approval. On this workshop repo, the workshop lead will merge yours.

Where it actually gets merged to

On this practice repo your branch merges straight into main, because there's nothing to deploy and nobody to break. Real client projects almost never work that way — a change is promoted through a series of environments, and each one is a chance to catch a problem before a customer does.

A typical three-stage setup:

feature/add-jane ──┐
                   ├──►  staging  ──►  main
feature/fix-nav  ──┘   (pre-prod)     (live)
   your work           team + client    real users
   in progress         testing here     see this
  • feature/* — one branch per piece of work. Yours. Nobody else is affected by it.
  • staging (also called pre-prod, UAT or develop) — a copy of the live site, on real infrastructure, with test data. Where QA happens and where you'd send a client for sign-off.
  • main — production. What actual users see. Guarded, usually with rules that prevent pushing to it directly.

Promoting a change, step by step

In practice each of these merges is a pull request on GitHub rather than typed locally — but this is what the PR is doing underneath: 

# STEP 1 — your feature is approved. Merge it into staging.
git checkout staging
git pull                                  # get whatever else landed first
git merge feature/add-jane-smith
git push origin staging

# --- the staging site rebuilds. Test it. Get client sign-off. ---

# STEP 2 — confirmed good? Promote staging to production.
git checkout main
git pull
git merge staging
git push origin main

# --- the live site rebuilds. Your change is out in the world. ---
The rule that makes this work Changes only ever flow one direction: feature → staging → main. Never the reverse. If something is broken in production you fix it on a new branch and promote the fix forward through the same path — you don't edit main directly, however tempting it is at 5pm on a Friday.

Why bother with the middle step?

Because "it worked on my laptop" is not evidence. Staging runs on the same infrastructure as production, so it catches the class of problem that only appears there: missing environment variables, a database that behaves differently at scale, an integration that was only ever mocked locally.

It's also simply where non-developers do their bit. When someone asks you to "check it on staging before we ship", this is the branch they mean.

Names vary, the shape doesn't You'll meet develop, uat, qa, preprod, release/*, and teams with four or five stages instead of two. Some call production master or prod rather than main. The vocabulary changes between companies; the one-directional flow is the constant. Ask which branch deploys where — it's a normal question, and the answer is often undocumented.

Merge conflicts

If two people changed the same lines, Git won't guess which version is right. It stops and asks. You'll see markers like this in the file: 

<<<<<<< HEAD
their version of the line
=======
your version of the line
>>>>>>> feature/add-jane-smith

Delete the markers and leave the text you actually want — often both lines, one after the other. Then: 

git add team.html
git commit -m "Resolve merge conflict in team page"
A conflict is not a mistake It means two people were working productively at the same time. Every developer resolves these regularly. Hitting one during the workshop is good practice, not a problem.

After merging

git checkout main   # go back to the main branch
git pull            # collect your change, now merged in

Your work is now part of the project, and its history records that you did it. That's the loop complete.
