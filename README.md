## Who This Is For

You do **not** need to be a developer. This workshop is built for designers, strategists,
researchers and anyone else who works alongside engineers and keeps getting handed GitHub
links they can't do anything with.

The site itself is deliberately simple — plain HTML and CSS (plus about thirty lines of
JavaScript on one page), no frameworks, no build step, nothing to install. That's on purpose:
the point isn't the website, it's the *workflow* around it. Every file in here is commented to
explain what it does and why, so the code doubles as the teaching material.

## Git in 60 Seconds

Five words do most of the work. If you understand these, everything else is detail.

| Word | What it actually means |
|---|---|
| **Repository** ("repo") | A project folder that tracks its own history. This whole thing is a repo. |
| **Commit** | A save point with a note attached. Like "Save As" but it never overwrites — you keep every version. |
| **Branch** | Your own copy to experiment in, so you can't break what everyone else is using. |
| **Push / Pull** | Upload your commits to GitHub / download everyone else's. |
| **Pull Request** ("PR") | "Here's my change, please review it before we make it official." |

The normal rhythm of work:

```
branch  →  edit  →  commit  →  push  →  pull request  →  review  →  merge
```

You'll do that full loop today.

## First Setup

**One time only.** Skip to Quick Start if you've done this before on this computer.

### 1. Install Git

- **Windows** — download from [git-scm.com](https://git-scm.com/download/win). Accept the defaults.
- **macOS** — open Terminal and run `git --version`. If Git isn't installed, macOS offers to install it.
- **Linux** — `sudo apt install git` (or your distro's equivalent).

Check it worked:

```bash
git --version
```

If you see a version number, you're good. If you see "command not found", see
[Troubleshooting](#troubleshooting).

### 2. Tell Git who you are

Git stamps your name onto every commit you make. Without this it refuses to commit at all.

```bash
git config --global user.name "Your Name"
git config --global user.email "your.email@nilehq.com"
```

Use the same email as your GitHub account, otherwise your commits won't be linked to your
profile. `--global` means "for all my projects", so you only do this once.

### 3. Sign in to GitHub

GitHub stopped accepting account passwords over the command line in 2021, so typing your
normal password when it asks **will not work**. Pick one of these instead:

**Easiest — GitHub CLI:**

```bash
# Install from https://cli.github.com, then:
gh auth login
```

Follow the prompts (choose HTTPS, then "Login with a web browser"). This handles everything
and you never think about it again. Recommended if you're not sure.

**Alternative — Personal Access Token:**

1. Go to GitHub → Settings → Developer settings → Personal access tokens → Tokens (classic)
2. **Generate new token**, tick the **repo** scope, set an expiry
3. Copy the token — you can't see it again after you leave the page
4. When Git asks for a "password", paste the token instead

Treat that token like a password. Don't paste it into Slack, a document, or a file in this repo.

## Quick Start

The whole loop, start to finish. Copy these one at a time and read what each one prints.

```bash
# 1. Download the project to your computer
git clone https://github.com/RCNile/AI-Academy-Using-Github.git

# 2. Move into the folder you just downloaded
cd AI-Academy-Using-Github

# 3. Make your own branch to work in (use your own name)
git checkout -b feature/add-jane-to-team

# 4. --- now edit team.html in your text editor and save it ---

# 5. See what you changed
git status
git diff

# 6. Stage the file (choose what goes into your next save point)
git add team.html

# 7. Commit it (write the save point, with a message)
git commit -m "Add Jane Smith to the team page"

# 8. Upload your branch to GitHub
git push origin feature/add-jane-to-team
```

Git will print a link at the end of step 8. Open it, and you're on the Pull Request screen.
Write a sentence about what you did, click **Create pull request**, and you're done — you've
just completed the same workflow professional engineering teams use every day.

> **Why `git add` and then `git commit`?** Two steps feels redundant at first. It's so you can
> commit *some* of your changes and not others — if you edited four files but only two are
> finished, you stage those two. `git add` is "put this in the box", `git commit` is "seal the box".

## Run It Locally

No server needed and nothing to install. The browser can open the files directly:

| Your setup | Command |
|---|---|
| Windows | `start index.html` |
| macOS | `open index.html` |
| Linux | `xdg-open index.html` |
| WSL | `explorer.exe index.html` |

Or double-click `index.html` in your file browser. Links between Home, About and Team are
relative, so navigation works fine this way.

The one piece of JavaScript in the project is the card generator on `team.html`. It's plain
vanilla JS in a `<script>` tag — no framework, no build step — and it works fine opened as a
local file. The only thing that degrades is the "Copy to clipboard" button: browsers restrict
clipboard access on `file://` pages, so it falls back to selecting the text for you to copy
with <kbd>Ctrl</kbd>+<kbd>C</kbd>. That fallback is deliberate, and commented in the file.

### If you'd rather use a local server

Optional. Not needed here, but a good habit for later projects that *do* require one:

```bash
python3 -m http.server 8000
```

Then open **http://localhost:8000/**.

> **Don't use `http://0.0.0.0:8000/`.** `0.0.0.0` is the address the server *listens* on, not
> one a browser can visit — you'll get `ERR_ADDRESS_INVALID`. Always browse to `localhost`.

> **WSL users:** serving from a `/mnt/c/...` path is slow, because every file read crosses from
> Linux to Windows. Either open the file directly (table above), or copy the repo into your Linux
> home first (`cp -r . ~/portfolio && cd ~/portfolio`) and serve from there. That copy is a
> *separate* checkout — commit from the original if you want your work tracked.

## Project Structure

```
AI-Academy-Using-Github/
│
├── README.md         # You are here. Every repo should have one.
│                     #   What the project is, how to run it, how to contribute.
│                     #   GitHub renders this automatically on the repo homepage.
│
├── .gitignore        # Which files Git should pretend don't exist.
│                     #   Security-critical — this is what keeps .env out of Git.
│
├── .env.example      # Template listing the config the project needs.
│                     #   Committed on purpose; holds only fake values.
│
├── index.html        # Homepage. The six core Git ideas as clickable cards —
│                     #   each opens a reference modal with commands, common
│                     #   mistakes, and how branches get promoted to production.
├── about.html        # Why version control matters, in plain English.
├── team.html         # ★ YOUR PRACTICE GROUND — add yourself to this one.
│                     #   Includes a form that writes your HTML snippet for you.
│
└── styles.css        # All the styling, shared by all three pages.
                      #   Colours and fonts are CSS variables at the top.
```

**Some things to notice about that layout:**

- **`README.md` sits at the root.** GitHub looks for it there and renders it on the repo
  homepage. It's the first thing anyone sees, so it's the most valuable file in the project.
- **One stylesheet, three pages.** Change a colour in `styles.css` and all three update.
  That's why styling doesn't go inside the HTML files.
- **`.env.example` is committed, `.env` is not.** The single most important convention here.
- **Files starting with a dot are hidden** by default on macOS and Linux. VS Code shows them
  normally. In Finder, press <kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>.</kbd> to reveal them.
- **No `src/`, no `dist/`, no config files.** Real projects accumulate these. This one stays
  flat so there's nothing to navigate.

## Environment Variables

Real projects need secrets — database passwords, API keys. Those must **never** go into Git.

The convention, which this repo demonstrates:

- **`.env`** holds your real secrets. It's listed in `.gitignore`, so Git ignores it completely.
- **`.env.example`** holds fake placeholder values. It *is* committed, so your teammates can see
  which variables they need to fill in without you ever sending them a password.

```bash
cp .env.example .env
# then open .env and fill in the real values
```

This site doesn't actually read any of them — `.env.example` is here to teach the pattern,
because you'll see it in nearly every real repo you touch.

## Troubleshooting

Real errors you're likely to hit, and what they mean in plain English.

<details>
<summary><strong>git: command not found</strong></summary>

Git isn't installed, or your terminal was open before you installed it. Install it (see
[First Setup](#1-install-git)), then **close and reopen your terminal** — it only picks up
newly installed programs on startup.
</details>

<details>
<summary><strong>Support for password authentication was removed</strong></summary>

You typed your GitHub account password. GitHub stopped accepting those over the command line
in 2021. Use `gh auth login`, or generate a Personal Access Token and paste that where it asks
for a password. See [Sign in to GitHub](#3-sign-in-to-github).
</details>

<details>
<summary><strong>Permission denied (publickey)</strong></summary>

You're using an SSH URL (`git@github.com:...`) but haven't set up an SSH key on this machine.

Easiest fix — switch to HTTPS instead:

```bash
git remote set-url origin https://github.com/RCNile/AI-Academy-Using-Github.git
```

Then authenticate with `gh auth login` or a token.
</details>

<details>
<summary><strong>remote: Repository not found</strong></summary>

Three possible causes, in order of likelihood:

1. **Typo in the URL.** Copy it from the green **Code** button on GitHub rather than typing it.
2. **The repo is private and you don't have access.** Ask to be added as a collaborator.
3. **You're signed in as the wrong account.** Run `gh auth status` to see who Git thinks you are.
</details>

<details>
<summary><strong>fatal: not a git repository</strong></summary>

You're in the wrong folder. Git commands only work *inside* a repo. Run `pwd` (macOS/Linux) or
`cd` (Windows) to see where you are, then `cd AI-Academy-Using-Github`.

Classic version of this: you cloned, then forgot step 2 and never moved into the folder.
</details>

<details>
<summary><strong>Please tell me who you are</strong></summary>

You skipped setup step 2. Git won't commit anonymously:

```bash
git config --global user.name "Your Name"
git config --global user.email "your.email@nilehq.com"
```
</details>

<details>
<summary><strong>fatal: destination path 'AI-Academy-Using-Github' already exists</strong></summary>

You already cloned it. You don't need to clone again — just `cd AI-Academy-Using-Github` and
get the latest changes:

```bash
git checkout main
git pull
```
</details>

<details>
<summary><strong>Updates were rejected because the remote contains work that you do not have</strong></summary>

Someone else pushed since you last downloaded. Get their changes first, then push again:

```bash
git pull
git push
```

Never reach for `git push --force` to make this go away — it deletes their work.
</details>

<details>
<summary><strong>CONFLICT (content): Merge conflict in team.html</strong></summary>

You and someone else edited the same lines. Git doesn't guess — it asks you to choose.

Open the file and look for these markers:

```
<<<<<<< HEAD
their version
=======
your version
>>>>>>> your-branch
```

Delete the markers and leave the text you want (often both, one after the other). Then:

```bash
git add team.html
git commit -m "Resolve merge conflict in team page"
```

This is normal and happens to everyone. It is not a sign you broke something.
</details>

<details>
<summary><strong>I committed my .env file by accident</strong></summary>

**Rotate the secrets first.** Anything pushed to GitHub should be treated as public forever —
deleting the file later doesn't remove it from the repo's history. Regenerate the API key,
change the password.

Then remove it from tracking (this keeps your local copy):

```bash
git rm --cached .env
git commit -m "Remove .env from version control"
git push
```

Then tell whoever runs the repo, so they can scrub the history properly. Nobody will be cross —
this is exactly why `.gitignore` exists, and it's a good lesson to have had early.
</details>

<details>
<summary><strong>warning: LF will be replaced by CRLF</strong></summary>

Harmless. Windows and macOS/Linux mark the end of a line differently, and Git is translating
between them. Ignore it.
</details>

<details>
<summary><strong>My change doesn't show up in the browser</strong></summary>

In order of likelihood:

1. **You didn't save the file.** Check for a dot or asterisk on the editor tab.
2. **The browser cached the old version.** Hard refresh: <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd>
   (Windows/Linux) or <kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>R</kbd> (Mac).
3. **You're looking at a different copy of the file** than the one you edited.
</details>

<details>
<summary><strong>I'm completely lost and want to start over</strong></summary>

Throw away all uncommitted changes and return to a clean copy of `main`:

```bash
git checkout main
git reset --hard origin/main
git pull
```

This **permanently deletes** uncommitted work, which is what you want here but not usually.
Anything you already committed is safe.
</details>

### Two commands worth memorising

```bash
git status    # What's changed? What branch am I on? What do I do next?
git log --oneline --graph --all    # Show me the history
```

`git status` is genuinely helpful — it usually tells you the exact command you need next. When
you're stuck, run it before anything else.

## Contributing

1. **Create a branch** for your change

   ```bash
   git checkout -b feature/your-feature-name
   ```

2. **Make your changes** and commit them

   ```bash
   git add .
   git commit -m "Add your feature"
   ```

3. **Push your branch**

   ```bash
   git push origin feature/your-feature-name
   ```

4. **Open a pull request** on GitHub — use the link Git prints, or the banner on the repo page.
   Describe what you changed and why.

5. **Wait for review.** Someone will read it and may ask questions. That's collaboration, not
   criticism.

6. **Merge.** Once approved, your change becomes part of the project.

### Writing a good commit message

Finish the sentence *"If applied, this commit will…"*

| Good | Not so good |
|---|---|
| `Add Jane Smith to team page` | `update` |
| `Fix broken GitHub link in footer` | `fixed stuff` |
| `Explain PAT setup in README` | `asdfgh` |

Your future teammates read these to work out when something changed and why. Six months from
now, that includes you.
