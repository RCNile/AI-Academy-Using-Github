What Is This?

A demonstration project built for the Nile AI Academy GitHub Workshop. It's a small portfolio website whose real purpose is to give you something safe to practise on.

Working through it, you'll see:

  • How a real project is laid out on GitHub
  • What a genuinely useful README contains
  • Why .gitignore exists, and what happens when it's wrong
  • How secrets are handled with .env and .env.example
  • How a series of commits tells the story of a project
  • The pull request and code review workflow

Every file in this repo is heavily commented. Open any of them in a text editor — the comments explain what the code does and why it's written that way.

Why Learn GitHub If You Don't Write Code?

Because GitHub stopped being only for code a long time ago. At Nile it's where the actual work lives:

  • Client deliverables — prototypes, sites and tools we hand over
  • Design handover — seeing exactly what engineers built from your specs
  • Reviewing changes — commenting on work before it ships
  • History — answering "when did this change, and who decided that?"
  • Issues — the shared to-do list for a project
  • Documentation — READMEs, decisions, research notes
The practical payoff Being able to clone a repo, read a diff and leave a review comment changes how you work with engineers. You stop waiting for someone to export a screenshot for you.

The One Rule You Must Not Break

Everything else in this workshop is recoverable. This isn't, so it gets its own section.

Never commit a password, API key or token Once you push a secret to GitHub, treat it as public permanently. Deleting the file in a later commit does not help — Git keeps every previous version, and anyone can read it out of the history. Automated bots scan public repositories for leaked keys and find them within minutes.

This is what .gitignore is for. The pattern this repo uses:

  • .env holds your real values. It's listed in .gitignore, so Git ignores it completely.
  • .env.example holds fake placeholders. It is committed, so teammates can see which values they need to fill in.

Open both files in this repo and compare them — they're commented to explain every line.

If it happens anyway Change the secret immediately — regenerate the key, reset the password — then tell whoever runs the repo. Nobody will be annoyed with you. This is exactly why the convention exists, and it's a much better lesson to learn on a practice repo than a client one.

Version Control, Without the Jargon

You already understand version control. You've just done it by hand: 

proposal.docx
proposal-v2.docx
proposal-v2-FINAL.docx
proposal-v2-FINAL-actually-final.docx
proposal-v2-FINAL-clients-edits-JAN.docx

That's version control — badly. You can't tell what changed between any two files, who changed it, or why. Merging two people's edits means reading both side by side and hoping.

Git does the same job properly. One file, with every previous version kept alongside a note on what changed and who changed it. Two people can edit the same document and Git combines the results.

The five words that matter

  • Repository — a project folder that remembers its own history
  • Commit — a save point with a note attached; nothing is ever overwritten
  • Branch — your own copy to experiment in, safely
  • Push / Pull — upload your work / download everyone else's
  • Pull request — "here's my change, please review it"

The Workflow You'll Practise

Every professional software team, in some variation, does this:

Clone → Branch → Edit → Commit → Push → Pull Request → Review → Merge

What each step is actually for

  1. Clone — copy the project to your computer. Once per project, not once per change.
  2. Branch — make a private workspace. The team's version stays untouched while you experiment.
  3. Edit — do the work. Normal file editing, nothing special.
  4. Commit — save a snapshot with a message. Commit often; small commits are easier to review and easier to undo.
  5. Push — upload your branch so others can see it.
  6. Pull request — formally propose your change and open it for discussion.
  7. Review — a teammate reads it and may ask questions. Not criticism; this is how mistakes get caught cheaply.
  8. Merge — your change joins the main project.
Why branch at all? So that unfinished work is never in everyone's way. You could commit straight to main — and on a solo project people often do — but on a team it means your half-finished edit is instantly everyone's problem.

Writing a Commit Message People Thank You For

Finish this sentence: "If applied, this commit will…"

  • Add Jane Smith to team page — clear, specific
  • Fix broken GitHub link in footer — says what and where
  • Explain token setup in README — obvious why it exists

Compare those with:

  • update — update what?
  • fixed stuff — which stuff?
  • asdfgh — we've all done it. Try not to.
Who is this for? Whoever has to work out, six months from now, why a line changed. Often that person is you, and you will not remember.

How to Contribute

Reading about Git doesn't teach Git. Doing it once does. The Team page is built for exactly this — add yourself and you'll have completed the full loop.

cd AI-Academy-Using-Github
git checkout -b feature/add-your-name

# edit team.html, save it, then:
git add team.html
git commit -m "Add your name to team page"
